# 回滚手册（Rollback Manual）

> 目标：真出事时，不用动脑子，照着走就能把公网页面救回上一个正常版本。
> 适用范围：CloudBase 静态托管的前端页面（WordWorld v1.0 起）。
> 更新时间：2026-10-13（Day 26）

---

## 0. 先分清两件事（最容易搞混）

| 动作 | 管的是 | 能不能救公网 |
|---|---|---|
| **git 回退**（`git checkout` / `git revert`） | 你电脑上的**源代码** | ❌ 不能。代码回退了，线上还是坏的，因为没重新部署 |
| **静态托管回滚**（重传旧版 dist） | 公网用户看到的**部署产物** | ✅ 能。这才是"回滚" |

本手册讲的是**第二种**——只有它能救公网。

---

## 1. 前置条件（平时就要备好）

**没有这一步，出事了就回不去。** 每次正式发布前，必须先把"当前正常版"备份一份：

```bash
# 在项目根目录执行，把当前正常版 dist 存成快照
cp -r dist release-snapshots/<版本号>
```

快照目录已加入 `.gitignore`，不会误提交。**每次发布前备份上一版，是回滚的唯一保险。**

---

## 2. 回滚步骤（静态托管回退路径）

假设公网当前是 v1.0（出问题了），要回退到 v0.9（上一个正常版）：

1. **定位上一版快照**：`release-snapshots/v0.9/`（如果没有快照，用旧 commit 重新 build）
2. **打开 CloudBase 控制台 → 静态网站托管**
3. **清空当前托管里的文件**（index.html + assets/ + sprites/）
4. **上传快照里的全部内容**到同一层：
   - `index.html`
   - `assets/`
   - `sprites/`（如果该版本有）
5. **强刷浏览器验证**（`Ctrl + F5`，绕过缓存）
6. **记录耗时**（从"决定回滚"到"页面恢复"的分钟数）

---

## 3. 关键检查点（回滚后别急着说"好了"）

- [ ] 页面能打开，且**加载的是目标版本的资源**（看地址栏 + 页面内容）
- [ ] **强刷后**正常（排除浏览器缓存假象）
- [ ] 资产文件一个不少（尤其 sprites/，漏了会白屏或素材空白）
- [ ] 前端调用的接口仍与后端匹配（见下方"判断表"第 3 行）

---

## 4. 什么情况必须回滚（判断表）

| # | 情况 | 必须回滚？ | 为什么 |
|---|---|---|---|
| 1 | 页面**白屏**、打不开、报 JS 错误 | ✅ 是 | 用户完全用不了，零容忍 |
| 2 | 核心功能坏了（输入英文→生成物体 不工作） | ✅ 是 | 这是产品的命脉，坏了等于产品不存在 |
| 3 | 前端调了**后端没有的接口**（前后端版本不匹配） | ✅ 是 | 会持续报错，且修后端要更久 |
| 4 | 素材/资源大面积缺失（图片全空白） | ✅ 是 | 影响观感且通常指向部署遗漏 |
| 5 | 只是**样式小瑕疵**（配色、间距不对） | ❌ 否 | 可以下一个补丁修，不必回滚 |
| 6 | **数据/后端**出了问题 | ⚠️ 看情况 | 回滚静态托管救不了后端，要走数据恢复流程（本手册不覆盖，另备查） |
| 7 | 新功能正常，只是**某个新功能有 bug** | ⚠️ 看情况 | 若不影响核心流程，可先禁用该功能，不必整体回滚 |

**一句话规则**：**"白屏 / 核心功能坏 / 前后端不匹配" 三者之一出现 → 立即回滚；纯样式或单功能小 bug → 优先补丁，不回滚。**

---

## 5. 回滚后的"恢复 v1.0"

回滚只是急救，不是终点。恢复流程：

1. 修好问题 → 重新 `npm run build`
2. 备份当前快照（把这次教训也存档）
3. 重新上传到静态托管
4. 验证 + 记录

---

## 6. 今日不做的（备查，另行补全）

- **云函数回退**：云函数（api-assets / api-favorites）的回退需在 CloudBase 控制台"函数服务→版本/流量"里操作，本手册暂不覆盖。
- **数据恢复**：PostgreSQL 数据的恢复走 CloudBase 数据库"备份/回档"，需单独流程。
